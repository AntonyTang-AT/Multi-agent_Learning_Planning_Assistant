## 0. 产品场景与答辩主线

**产品名建议**（可改）：高数/大物学习计划多智能体助手

**两大使用场景**（需求与演示都围着转）：

| 场景 | 用户说法示例 | 系统要帮的事 |
|---|---|---|
| **期末复习** | 「两周后高数期末，每天最多 2 小时，想过线」 | 按考点出复习计划、组卷/刷题、冲突时让用户改时间或降深度 |
| **跟课补漏** | 「这周导数没听懂，作业不会，想跟上进度」 | 按当前章节补概念+基础题，负荷高时拆任务、插入回顾 |

**一句话创新**：别人的多 Agent 在分工生成；我们的在分工质疑、校验和协商——冲突与不可靠答案显式暴露，用户裁决。

**3 分钟答辩结构**：

| 时段 | 内容 | 负责准备 |
|---|---|---|
| 0:00–0:40 | 场景痛点（期末/跟课） | 5 号主写 |
| 0:40–1:10 | 两种方案比较 → 本方案 | 5 号 + 3 号 |
| 1:10–2:20 | 核心功能演示 | 1 操作，2 数据通路，3 智能内核，5 控场 |
| 2:20–3:00 | 创新、安全、改进 | 5 号 + 3 号 |

## 1. 角色总览（5 人）与硬边界

```text
用户 ←→ [1 前端 Web] ←→ [2 传统后端：读写/存盘/转发] ←→ [3 AI·多智能体系统：唯一智能内核]
                              ↑
                         [4 资料包：宽覆盖结构化数据]
```

| 编号 | 角色 | 主责（一句话） | 明确**不做** |
|---|---|---|---|
| **1** | 前端 | 学习助手界面、演示动线、调 2 号 API 展示与操作 | 不直连 LLM；不写 Agent 逻辑 |
| **2** | 后端 | **传统 Web 服务**：账号/会话、业务数据 CRUD、文件/库存储、把请求转给 3 号并原样/映射回传 | **不写提示词、不编排 Agent、不做校验/出题/计划智能** |
| **3** | 多智能体 | **全部 AI 能力**：编排、计划、检索意图、出题、计算检验、记忆推理、评估质疑、黑板智能写入；**只暴露 I/O 接口** | 不管前端样式；不替代 2 号做用户表/文件永久存储规范（可返回结果由 2 落库） |
| **4** | 资料 | 高数+大物：**课件/教材/习题/真题尽量宽覆盖**，整理成软件可检索、可组计划、可刷题的数据包 | 不写业务后端；不调 LLM（标注与结构化为主） |
| **5** | 海报/PPT/答辩 | 需求分析（期末/跟课）、方案比较、A2 海报、PPT、3 分钟稿 | 不扛核心编码；内容须与真功能一致 |

**协作原则**：

- **智能全在 3**：1、2 眼中的「AI」= 一次 HTTP（或等价）调用的 **请求 JSON → 响应 JSON**。  
- **2 号像普通业务后端**：存计划、存作答、存用户选项、存 3 号返回的快照；需要智能时 **转发 I/O**，自己不理解 Agent 内部。  
- **12 号检查点**：1+2 像正常学习助手一样能跑通「读资料、看计划、做题、存记录」；接上 3 号后同一套 UI 出现智能结果。  
- **接口先行**：先锁 2↔3 的 I/O 与 1↔2 的业务 API，再并行。

## 2. 1 号 · 前端（Web）

### 2.1 定位

面向期末复习 / 跟课补漏的 **Web 学习助手壳**：对话、计划、题库练习、学习记录、冲突/干预卡片、黑板列表；只与 **2 号后端**通讯。

### 2.2 页面（MVP）

| 模块 | 说明 | 优先级 |
|---|---|---|
| 场景入口 | 选「期末复习」或「跟课补漏」，填约束（考试日/当前章节/每日时长） | P0 |
| 对话区 | 展示用户话 + 系统回复（内容来自后端转发的 3 号输出） | P0 |
| 计划页 | 展示已保存计划；冲突时展示后端下发的选项并提交裁决 | P0 |
| 练习页 | 选题/做题/交卷；展示通过、提示模式、弃答等状态文案 | P0 |
| 资料浏览 | 按章节/知识点浏览 4 号资料（纯读后端数据） | P1 |
| 轨迹/掌握度 | 读后端已存记录做简单展示 | P1 |
| 黑板面板 | 展示后端保存的黑板条目与状态 | P0 |
| 演示控制 | 时间跳跃等（调后端 demo 接口；智能仍在 3） | P0 |

### 2.3 通讯

- 只调 2 号；统一错误/超时提示。  
- 3 号挂了时：后端应返回业务错误或缓存快照，前端展示「智能服务暂不可用」，本地资料与已存计划仍可看。

### 2.4 12 号验收

- [ ] 场景入口 + 计划 + 做题 + 记录主路径可点  
- [ ] 与 2 号真实联通至少：读资料/存计划/提交作答  
- [ ] 智能相关按钮在 3 号就绪后无需改架构即可接上

## 3. 2 号 · 后端（传统 Web，非 AI）

### 3.1 定位（请按此理解职责）

做**常规学习网站后端**，不是智能系统：

| 做 | 不做 |
|---|---|
| 用户/会话（可简化） | 提示词工程 |
| 资料索引与题目的 **读写、导入、查询** | Agent 路由 / 多 Agent 对话 |
| 计划、作答、轨迹、黑板条目的 **持久化** | SymPy 校验、质疑规则、负荷信号计算 |
| 接收前端操作 → 若需 AI，则 **组装输入调用 3 号 → 把输出存盘并返回前端** | 解析或改写 3 号内部状态机 |
| 静态/上传文件、CORS、部署、健康检查 | 持有并消费「业务提示词」（若代理 Key，也仅做透传网关，逻辑仍算 3） |

> **推荐**：LLM API Key 与模型调用 **只放在 3 号进程**。2 号配置项仅有 `AGENT_BASE_URL`。若学校环境必须由 2 号出网，也只做 **HTTP 透传**，请求体/响应体 schema 仍由 3 号定义，2 号不解析业务字段含义。

### 3.2 模块（传统软件视角）

| 模块 | 职责 |
|---|---|
| `users/session` | 登录或访客 id |
| `materials` | 导入/查询 4 号资料与题目（章节、知识点、关键词） |
| `plans` | 保存/读取/更新用户计划（内容可来自 3 号输出快照） |
| `attempts` | 保存作答、对错、耗时、用户选择的错因等 |
| `blackboard` | 保存 3 号返回的条目；用户裁决后更新 status |
| `agent_gateway` | **唯一与 AI 相关的薄封装**：`forward(intent, payload) → raw result`，超时与错误码 |
| `demo` | 切换演示用户、灌入已存快照（可选） |

### 3.3 和 3 号的关系（只认 I/O）

```text
前端「生成期末计划」 
  → 2 号：校验用户已填考试日/时长等业务字段，写入 pending
  → 2 号：POST 3号 /invoke  { intent, input, 必要的资料引用 id }
  → 3 号：内部跑多智能体，返回 { status, output, blackboard_entries, user_options, ... }
  → 2 号：把 output/黑板 写入 SQLite，把同一结果返回前端
  → 前端：渲染；用户点选项后，2 号存裁决，必要时再 forward 一次 arbitrate
```

2 号**不需要知道**里面有几个 Agent；只保证：**输入送得出、输出存得下、前端读得到**。

### 3.4 12 号验收

- [ ] 无 3 号时：资料浏览、手动/导入计划 CRUD、做题存记录 **完整可用**（像普通学习站）  
- [ ] 有 3 号时：`agent_gateway` 能通，结果落库可查  
- [ ] `docs/api.md`（给前端）发布；错误体统一  
- [ ] 能导入 4 号宽覆盖数据包

## 4. 3 号 · 多智能体系统（全部 AI，只留 I/O）

### 4.1 定位

**项目智能内核的唯一所在地**。计划生成、资料检索策略、出题、计算检验、结构化质疑、元认知/主动干预、认知负荷与动机信号、共享黑板的智能写入等，**全部在此进程内完成**。

对外形态：独立服务 + **稳定输入输出接口**（给 2 号调用）。  
对内：主 Agent + 计划/搜索/出题/检验/记忆/评估 + 黑板（见形式化方案）。

### 4.2 对外 I/O（示意）

**请求（输入）**只应包含业务侧已准备好的事实，例如：

```json
{
  "request_id": "uuid",
  "scenario": "final_review|catch_up",
  "intent": "create_plan|generate_question|verify_answer|metacognitive_feedback|proactive_intervention|arbitrate|...",
  "user_profile": { "user_id": "", "constraints": {} },
  "input": { },
  "resource_refs": ["knowledge_id或question_id列表，由2号从资料库查出后传入"],
  "trace_snapshot": { }
}
```

**响应（输出）**只应包含前端/后端可直接消费的结果，例如：

```json
{
  "request_id": "uuid",
  "status": "ok|conflict|doubt|failed|abstain|need_user",
  "output": { },
  "blackboard_entries": [],
  "user_options": [],
  "evidence_refs": [],
  "requires_approval": true
}
```

内部用 CrewAI/规则/SymPy/LLM 均可，**不泄漏给 2 号**。

### 4.3 场景相关能力

| 场景 | 3 号侧重点 |
|---|---|
| 期末复习 | 考点覆盖计划、时间预算审计、组卷难度、冲突协商选项 |
| 跟课补漏 | 当前章节先修检查、低门槛启动任务、负荷信号、概念回顾插入 |

### 4.4 交付与验收

- [ ] 独立可启动；提供 `docs/agent-api.md` + 示例 JSON  
- [ ] 必演：审计冲突、校验弃答、错因策略差异（质疑/干预有余力再加）  
- [ ] 输入缺失时返回明确 `status` + 可读 `message`，不让 2 号猜

## 5. 4 号 · 资料搜集与整理（宽覆盖）

### 5.1 目标调整

**尽量宽泛**，服务两类场景，而不是「只深挖一小节」：

- **期末复习**：章节考点清单、历年题型分布感、复习用题与真题拆解、公式/要点卡片。  
- **跟课补漏**：按课次/教材章节对齐的课件要点、课堂例题、课后习题、易错点。

高数、大物 **两条线都建**，深度可以「骨架宽 + 若干章题量够用」，避免只做一个知识点无法支撑场景叙事。

### 5.2 建议覆盖面（可按学校实际课表裁剪）

**高等数学（宽）**

- 知识点骨架：函数与极限、导数与应用、积分、微分方程、级数等（按本校大纲列全级标题）。  
- 每章：要点摘要、课件/教材出处元数据、例题+习题若干、期末常考标记 `exam_hot: true/false`。  
- 真题：至少整理「可检索的真题题单/拆题」若干套元数据（题干结构化优先）。

**大学物理（宽）**

- 骨架：力学、热学、电磁学、振动波动、光学等（按本校开课范围）。  
- 同样：要点、例题习题、跟课章节标签 `lecture_week` / `textbook_section`、期末热点标记。

数量不追求「全校题库」，但追求 **章章有入口、场景能选得动**。

### 5.3 目录约定

```text
data/
  README.md                 # 场景用法、导入方式、版权声明
  taxonomy/
    math_outline.json       # 宽覆盖知识点树 + 先修边
    physics_outline.json
  materials/                # 课件/教材摘录元数据（合规）
  questions/                # 习题与例题（带场景标签）
  exams/                    # 真题与期末向题目
  catch_up/                 # 可选：按周次/课次聚合的补漏包
  final_review/             # 可选：按考点聚合的复习包
  scripts/validate_schema.py
```

### 5.4 关键字段（方便 2 号存、3 号用）

题目/资料除原有字段外，增加场景相关标签：

| 字段 | 用途 |
|---|---|
| `scenario_tags` | `["final_review"]` / `["catch_up"]` / 两者都有 |
| `chapter` / `section` | 跟课对齐 |
| `lecture_week` | 可选，第几周内容 |
| `exam_hot` | 期末高频 |
| `knowledge_ids` | 挂到宽大纲 |
| `difficulty` / `type` / `error_tags` | 练习与演示 |
| `assumptions` / `verify_hint` | 给 3 号校验与质疑 |
| `source` / `license_note` | 合规 |

### 5.5 「整理效果」验收（宽覆盖版）

1. **大纲宽**：高数、大物均有完整章级（或课级）目录，可按章浏览。  
2. **场景能用**：存在可一键筛选的「期末复习包」「跟课补漏包」（或等价标签查询）。  
3. **软件可导入**：统一 JSON + `validate_schema.py`；2 号按章/标签查询即可。  
4. **智能可消耗**：带 `knowledge_ids`；部分题含 `verify_hint`；若干缺假设样例；错因标签多样。  
5. **合规说明写进 README**：摘录范围、是否改编、合成数据标注。

> 演示仍可「一章题量更密」，但 **对外叙事与数据包结构是全课程骨架**，避免被问「只有一小节怎么叫复习助手」。

### 5.6 交接

- → 2 号：整包 + 导入说明 + 查询字段说明  
- → 3 号：`resource_refs` 样例、校验题、质疑题、错因表  
- → 1/5 号：章节列表与场景筛选方式（做 UI 文案与海报）

## 6. 跨角色接口契约

### 6.1 前端 ↔ 后端（业务 API，传统风格）

| API | 作用 |
|---|---|
| `POST /api/session` | 访客/登录 |
| `GET /api/materials` | 按章/场景标签查资料 |
| `GET /api/questions` | 筛选题目 |
| `GET/PUT /api/plans/current` | 读/改已存计划 |
| `POST /api/attempts` | 提交并保存作答 |
| `GET /api/blackboard` | 读已存黑板 |
| `POST /api/blackboard/{id}/resolve` | 保存用户裁决 |
| `POST /api/ai/{intent}` | **仅转发**：body 交给 3 号，响应落库后返回（2 号不解读智能字段） |
| `GET /api/health` | 含 `agent: up/down` |

### 6.2 后端 ↔ 3 号（纯 I/O）

仅 `POST /agent/v1/invoke`（或少量等价 path）。  
2 号禁止在网关里写「如果 conflict 就本地改计划」之类智能分支——冲突选项来自 3 号 `user_options`，用户决定后 2 号只存结果，需要再算就再 invoke。

### 6.3 资料 → 后端

启动导入或管理接口导入；3 号通过 2 号传入的 `resource_refs` + 必要文本字段工作，也可在约定下由 3 号只读共享 `data/`（若同机部署）——**二选一写进 README，避免两套真相**。

## 7. 5 号 · 海报 / PPT / 答辩稿

### 7.1 需求叙事（按新场景）

- 痛点 A：期末临近，资料散、计划拍脑袋、刷题无体系。  
- 痛点 B：课上没听懂，作业硬拖，越补越乱。  
- 用户证据：访谈/问卷（室友、同学）各若干条即可。

### 7.2 方案比较（保留考核要求）

| 维度 | 方案 A：单模型聊天复习 | 方案 B：Web 学习站 + 独立多智能体校验协商 |
|---|---|---|
| 可行性 | 高 | 中（职责分离后更清晰） |
| 实用性 | 能问不能管计划可信度 | 计划可审计、答案可弃答、记录可沉淀 |
| 创新性 | 低 | 质疑/校验/黑板/用户裁决 |
| 安全 | 幻觉直接出口 | AI 封装在 3 号，门禁后出 |
| 成本 | 低 | 中 |

### 7.3 海报要点

场景双入口 → 传统 Web 存数据 + AI 内核 I/O → 演示截图（冲突/弃答）→ 安全边界 → 五人分工。

### 7.4 PPT / 3 分钟稿

突出：**壳与核分离**（2 传统 / 3 智能）也是工程合理性卖点；演示仍按必演动作，不按功能清单报菜名。

## 8. 时间线（12 号 + 答辩）

| 阶段 | 1 前端 | 2 后端 | 3 多智能体 | 4 资料 | 5 材料 |
|---|---|---|---|---|---|
| 接口锁定 | 线框：期末/跟课两入口 | 业务 API + gateway 空壳 | I/O schema 定稿 | 大纲宽表 + 标签约定 | 场景访谈 |
