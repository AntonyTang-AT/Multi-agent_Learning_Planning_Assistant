下面给出一份可直接用于团队对齐和答辩材料的**形式化整体方案**。它把你们已确定的“主Agent + 计划/搜索/出题/计算检验/记忆 + 评估Agent”作为骨架，并把**共享黑板、认知负荷/动机信号、结构化质疑、元认知反馈、主动干预**作为五个新增机制嵌入，而不是简单增加Agent节点。

# 学习计划多智能体系统·形式化整体方案

## 1. 定位与创新叙事

**系统定位**：面向高数/大物的学习计划多智能体系统。用户以自然语言提出目标与约束，系统生成计划、绑定题目与资料、记录并分析学习轨迹，并通过独立校验与质疑机制保证输出可靠；当计划不可行或答案不可靠时，系统不偷偷修改，而是显式暴露冲突、降级或弃答，并由用户裁决。

**一句话创新叙事**：

> **别人的多Agent在分工生成，我们的多Agent在分工质疑、校验和协商。系统不只执行计划，它在持续地感知执行状态、发起结构化质疑、把决策权交还用户，并在用户缺席时主动巡检。**

**五个新增机制的定位**：
- 共享黑板：让Agent协作过程**可见、可追溯**。
- 认知负荷/动机信号：让计划Agent从“只看知识状态”升级为**同时看执行状态**。
- 结构化质疑：让评估Agent从“打分者”扩展为**质疑发起者**。
- 元认知反馈：系统不替用户做所有决定，而是**把结构化选项交还用户**。
- 主动干预：系统在用户未提问时也能**基于记忆与评估发起建议**，但最终由用户裁决。

---

## 2. 总体架构

采用**Supervisor-Worker为主干、关键子链路为Pipeline、全局共享黑板**的混合编排。

```
用户
  │ 自然语言
  ▼
主Agent（Orchestrator / 唯一用户接口）
  │ 结构化消息路由
  ├──▶ 计划Agent ──▶ 审计/冲突协商 ──▶ 用户裁决
  ├──▶ 搜索Agent（共享服务：资料检索）
  ├──▶ 出题Agent ──▶ 计算检验Agent ──▶ 评估Agent（结构化质疑）
  ├──▶ 记忆Agent（轨迹记录、双库写入、状态供给）
  └──▶ 评估Agent（质疑、元认知反馈、主动干预触发）
          ▲
          │ 读写
   ┌──────┴──────┐
   │  共享黑板     │  ← 所有Agent可读写阶段性结论、疑点、冲突、待验证假设
   └─────────────┘
```

**控制流原则**：
- 主Agent负责意图识别、任务分解、结构化路由、结果综合；不直接做业务生成。
- 计划生成后**必须**经过审计检查，不直接写入用户计划。
- 出题Agent的题目与答案**必须**经过计算检验Agent；评估Agent可对“依赖未声明假设”等发起结构化质疑。
- 记忆Agent既存长期记忆，也存任务状态；评估Agent读取轨迹与黑板，触发元认知反馈或主动干预。
- 共享黑板是**跨Agent的公共工作区**，不替代消息，而是让“疑点、冲突、待验证假设、阶段结论”对全系统可见。

## 3. 角色职责与连接方式

| Agent | 核心职责 | 关键输入 | 关键输出 | 连接与约束 |
|---|---|---|---|---|
| **主Agent** | 唯一用户接口；自然语言→结构化任务；路由；综合结果；维护全局任务状态 | 用户对话、黑板摘要、任务状态表 | 结构化消息、用户可读回复、任务状态更新 | 不直接生成计划/题目；所有下游调用带`task_id` |
| **计划Agent** | 根据目标、硬约束、软偏好、认知负荷/动机信号生成计划草案 | 结构化目标、掌握度向量、负荷/动机信号、资料摘要 | 任务列表（动作+对象+时间+输出+完成标准+负荷档位） | 输出必须送审计；不得直接写用户计划 |
| **搜索Agent** | 为计划和出题提供资料/参考题检索；返回来源与可信度 | 检索意图、知识点、章节、难度 | 资料片段/参考题+来源+页码/可信度 | 共享服务；结果可写黑板 |
| **出题Agent** | 按知识点、难度、题型、错因目标生成题目与答案 | 知识点、难度、错因类型、参考题 | 题目+答案+假设声明+知识点标签 | 输出必须送计算检验；高风险题触发评估质疑 |
| **计算检验Agent** | 数值/符号验证；工具执行；步骤级规则校验 | 题目、答案、表达式、预设步骤 | 通过/存疑/不通过+差异点+审计轨迹 | 质量门禁；不通过时返回生成方或降级/弃答 |
| **记忆Agent** | 轨迹记录、掌握度更新、双库写入（官方库/个人库）、状态供给 | 作答记录、求助/修正行为、上下文 | 用户画像、掌握度、轨迹摘要、库写入结果 | 为计划/评估/主动干预提供状态 |
| **评估Agent** | 原“打分/评估”扩展为：结构化质疑发起、元认知反馈、主动干预触发、必要难度建议 | 黑板、轨迹、计划/题目、校验结果 | 质疑条目、元认知问题卡片、主动干预建议、难度调整建议 | 不生成替代方案；只指出问题/给结构化选项 |
| **共享黑板（隐式角色）** | 全系统可读写的公共工作区 | 各Agent写入 | 冲突、疑点、假设、阶段结论、待裁决项 | 所有关键动作留痕；演示可视化 |

**关键Pipeline**：
- 计划链路：`计划Agent → 审计（规则） → 冲突协商 → 用户裁决 → 计划重排`
- 出题链路：`出题Agent → 计算检验Agent → 评估Agent（结构化质疑） → 通过/修订/弃答`
- 学习链路：`用户作答 → 记忆Agent记录 → 掌握度更新 → 评估Agent读轨迹 → 元认知反馈/必要难度建议`
- 主动链路：`记忆Agent+评估Agent巡检 → 主动干预卡片 → 主Agent呈现 → 用户接受/拒绝`

## 4. 通信协议：结构化消息 + 共享黑板

### 4.1 结构化消息Schema

所有Agent间通信使用统一JSON，禁止自由文本作为唯一载荷。

```json
{
  "task_id": "uuid",
  "parent_task_id": "uuid|null",
  "sender": "orchestrator|planner|retriever|generator|verifier|memory|evaluator",
  "receiver": "planner|retriever|generator|verifier|memory|evaluator|orchestrator",
  "intent": "create_plan|search_material|generate_question|verify_answer|record_trace|challenge|metacognitive_feedback|proactive_intervention|arbitrate",
  "parameters": {},
  "context_ref": {
    "user_id": "u_001",
    "blackboard_refs": ["bb_001"],
    "memory_refs": ["trace_20261030"]
  },
  "constraints": {
    "hard": [],
    "soft": []
  },
  "output_schema": "plan.v1|question.v1|verify.v1|challenge.v1|feedback.v1",
  "trace": {
    "timestamp": "",
    "agent_version": ""
  }
}
```

**约定**：
- `intent`决定路由和输出schema。
- `constraints.hard`不可违反；`soft`可协商。
- 所有输出必须带`evidence_refs`（来源/页码/黑板条目ID/轨迹ID），便于审计与演示追溯。
- 高风险动作（写计划、写题库、写官方库）必须带`requires_approval: true`。

### 4.2 共享黑板Schema

黑板是全局公共工作区，建议用JSON/SQLite实现，前端可视化。

```json
{
  "entry_id": "bb_001",
  "task_id": "uuid",
  "type": "conflict|doubt|hypothesis|stage_conclusion|pending_arbitration|challenge|intervention",
  "author": "planner|verifier|evaluator|memory",
  "content": {
    "summary": "计划第3天超出每日45分钟预算",
    "evidence_refs": ["plan.v1#task3", "constraint#daily_time"],
    "severity": "high|medium|low"
  },
  "status": "open|resolved|rejected|deferred",
  "resolution": {
    "resolved_by": "user|auditor|evaluator",
    "action": "extend_time|reduce_depth|adjust_goal|retry|abstain",
    "note": ""
  },
  "created_at": "",
  "updated_at": ""
}
```

**黑板写入规则**：
- 审计冲突、校验不通过、评估质疑、元认知待裁决、主动干预建议**必须**写入黑板。
- 主Agent综合回复时读取`open`条目；用户裁决后更新`status/resolution`。
- 演示时展示黑板条目的“产生→流转→裁决”过程，作为协作可见性的核心视觉。

## 5. 核心状态机与流程

### 5.1 计划生成与冲突协商状态机

状态：`IDLE → PARSED → PLAN_DRAFTED → AUDITING → (PASSED | CONFLICT) → NEGOTIATING → REPLANNED → APPROVED`

- `AUDITING`检查：时间预算、前置依赖、任务完成标准、认知负荷连续高值、目标可行性。
- `CONFLICT`时写入黑板`type=conflict`，评估Agent可补充“冲突类型与替代方案建议”，主Agent向用户呈现结构化选项（延长时间/降低深度/调整目标/保持原计划但标记风险）。
- 用户裁决后更新约束库并重排；重排结果再次审计，最多循环2次，仍冲突则降级为“建议方案+风险说明”。

### 5.2 出题与校验状态机

状态：`GENERATING → VERIFYING → (PASSED | DOUBT | FAILED) → CHALLENGING → (REVISED | ABSTAINED | ESCALATED)`

- `VERIFYING`：计算检验Agent做数值/符号验证；可选步骤规则校验。
- `DOUBT`：评估Agent触发结构化质疑，条件例如“答案依赖题干未声明假设”“多解未说明”“边界条件缺失”。质疑写入黑板`type=challenge`。
- `FAILED`：不直接给用户答案；走“重试→降级为提示模式→弃答”三分支；弃答需带审计轨迹。
- `PASSED`：题目/答案可进入用户视野或题库，但需带来源与假设声明。

### 5.3 学习轨迹与元认知反馈流程

`作答/学习行为 → 记忆Agent记录 → 掌握度更新 → 评估Agent读取轨迹+黑板 → 触发元认知反馈或必要难度建议 → 主Agent以问题卡片呈现 → 用户选择`

元认知反馈触发条件示例：
- 同类错误连续≥3次且未求助/未回看资料；
- 做对但依赖提示比例连续偏高；
- 连续失败后出现放弃倾向（中断/跳过/长时间无操作）。

反馈形式不是命令，而是**结构化问题**：“你注意到……你希望系统下周加入概念回顾，还是先自己尝试另一种方法？”用户选择后写回黑板并影响计划。

### 5.4 主动干预流程（演示用巡检，不做常驻后台）

`记忆Agent+评估Agent巡检 → 生成干预建议 → 写黑板type=intervention → 主Agent在下次打开时呈现卡片 → 用户接受/拒绝/修改`

触发示例：
- 用户两天未登录且原计划将进入新章节；
- 某知识点中断率连续偏高；
- 计划中高负荷连续超过阈值。

演示可用“时间跳跃”模拟：展示“上次中断两次→系统建议明天改为基础题+概念回看→用户接受/保持原计划”。

## 6. 五个新增机制的规格

### 6.1 共享黑板
- 实现：JSON/SQLite + 读写API；前端展示条目列表与状态流转。
- 用途：冲突、疑点、假设、阶段结论、待裁决、质疑、干预。
- 演示价值：让“多Agent协作”可见，而不是只看到最终输出。

### 6.2 认知负荷/动机信号接入计划
- 信号（轻量滚动，不训练模型）：
  - 认知负荷代理：最近N次任务中断率、实际耗时/预估耗时偏差、连续高负荷任务数。
  - 动机代理：连续失败后的跳过/中断/长时间无操作、求助缺失、启动延迟。
- 计划Agent读取信号后调整：高负荷→降低新内容比例、拆任务、插入低负荷回顾；低动机→插入低门槛启动任务；必要难度→对“做对但依赖提示”的知识点安排延迟提取练习。
- 演示：同一掌握度，两种信号下生成不同计划。

### 6.3 结构化质疑（评估Agent扩展）
- 触发条件明确、证据标准明确；评估Agent不生成替代方案，只指出“哪里可能不对、缺少什么证据”。
- 质疑类型：未声明假设、多解未说明、边界条件缺失、前置依赖不成立、题目与知识点标签不一致、计划任务缺完成标准。
- 输出`challenge.v1`，写入黑板，返回生成方或主Agent。
- 演示：一道“看似正确但依赖未声明假设”的题被质疑，触发修订或弃答。

### 6.4 元认知反馈
- 目标：帮助用户计划、监控、评估自己的学习，而不是替用户决定。
- 形式：结构化问题卡片+选项；用户选择写回黑板并影响计划/推荐。
- 触发：反复同类错误且无求助、依赖提示偏高、放弃倾向。
- 演示：系统不直接改计划，而是问用户“加入概念回顾还是自己先试另一种方法”。

### 6.5 主动干预
- 不做常驻后台；用巡检函数+演示时间跳跃。
- 输入：记忆Agent轨迹摘要、评估Agent信号、黑板open条目。
- 输出：干预卡片（建议+理由+接受/拒绝/修改）。
- 演示：两天未登录后的主动建议；用户裁决后计划重排。

## 7. 数据模型与混合推荐

**核心表**：用户画像、知识点表（含先修/关联边）、题目表（知识点/难度/题型/易错类型/假设声明）、交互表（用户-题-对错-耗时-求助-修正-错因-上下文）、轨迹事件表、掌握度表、黑板表、双库表（官方库/个人库）。

**轨迹记录**：作答结果、错因类型、求助行为、修正行为、学习上下文、自评。每条记录必须能被推荐/计划/评估消费。

**混合推荐**：
- 冷启动：知识点关联骨架（先修/关联）做可解释推荐。
- 数据积累后：协同过滤（余弦/Jaccard）基于“错因向量+掌握度+求助行为”画像动态加权。
- 合成数据定位为“机制验证数据”，主动标注；交互表稀疏，埋入可发现错因模式群体。

## 8. 答辩演示动线（建议5个动作，3分钟取舍）

**必演三个核心动作**：
1. **审计拦截+冲突协商**：LLM生成漂亮但超时/缺完成标准的计划→审计标红→用户选择“延时间/降深度/调目标”→重排。
2. **校验拦截+弃答**：故意让模型算错→计算检验拦截→重试/提示/弃答；展示“不强行给答案”。
3. **错因驱动推荐与计划变化**：同一道题切换错因标签→推荐策略和计划插入不同；展示轨迹被消费。

**新增两个高价值动作（时间允许）**：
4. **结构化质疑**：题目依赖未声明假设→评估Agent质疑→修订/弃答，黑板可见。
5. **主动干预+元认知反馈**：模拟两天未登录→干预卡片；或连续同类错误无求助→元认知问题卡片→用户裁决→计划调整。

答辩叙事收束：**“系统不只生成，它审计、质疑、校验、协商；用户始终握有最终裁决权。”**

## 9. 技术栈与一周落地裁剪

**技术栈**：
- 编排：CrewAI起步（低学习曲线），架构图/状态机用LangGraph式流程图在PPT/海报显式化；有余力再将外层状态流抽到LangGraph。
- 前端：Gradio/Streamlit；黑板可视化用表格/卡片。
- 后端：FastAPI或Python服务；SQLite/JSON。
- LLM：DeepSeek API后端代理；规则引擎独立于LLM。
- 校验：SymPy/AST求值；步骤校验用预设规则。
- 推荐：知识点标签+难度过滤；协同过滤余弦/Jaccard跑合成矩阵。

**MVP裁剪**：
- 只做高数一章做深，大物只做迁移验证或口头扩展。
- 搜索Agent MVP可先做函数调用，不强制独立Agent节点。
- 反思/元认知反馈先用模板+可选LLM，保证稳定。
- 主动干预用演示脚本“时间跳跃”，不做后台常驻。
- 共享黑板先做JSON+前端只读展示，不做复杂并发。

**一周节奏**：
- 第1天：结构化消息+黑板schema+主Agent路由；跑通“自然语言→计划草案→审计拦截→重排”最小回合。
- 第2—3天：出题→计算检验→评估质疑链路；轨迹记录字段；错因→推荐/计划联动。
- 第4天：认知负荷/动机信号接入计划；元认知反馈卡片；黑板可视化。
- 第5天：主动干预演示脚本；混合推荐冷启动对比；前端打磨；录屏。
- 第6—7天：整合5个演示动作，排练3分钟路演与分工陈述。

## 10. 风险与必须锁定的边界

- **风险**：Agent交互状态组合爆炸。对策：锁定“审计拦截、校验弃答、错因驱动推荐”三个必演动作，其他链路可简化。
- **风险**：合成数据被质疑。对策：主动标注“合成仿真数据/机制验证”，保留生成脚本；不伪造真实日志。
- **风险**：校验层只像“调计算器”。对策：把“结果并列可见+失败降级/弃答+黑板留痕”做成产品设计。
- **风险**：多人协作核心单点。对策：接口先行、假数据先行、规则表与编排层分离；你维护核心规则，其他人做前端/数据/文档。
- **边界**：不诊断、不替代专业建议；不代写作业；教材/题目版权合规；AI生成标注；官方库写入需审批。

**方案收束**：这套形式化方案的核心不是“Agent更多”，而是**用共享黑板让协作可见、用负荷/动机信号让计划知冷知热、用结构化质疑让系统敢说不对、用元认知反馈把决策权交还用户、用主动干预让Agent有记忆也有主动性**。它保留了你们已确定的全部骨架，同时把创新点集中到“校验、质疑、协商、裁决”这条主线上。
